# Schema Reference — DuckDB Tables & Link Roles

> Referenced from CLAUDE.md §4. Read this when you need column-level detail,
> link-role semantics, or the complete table list. For the pipeline that builds
> these tables see `pipeline-reference.md`; for the underlying XML structure see
> `docs/agents/xml-schema.md`.

## All tables

The table names mirror the XML branches of the corresponding object types:

- **XMLMetadata** — Root attributes of the XML file (version, DDR-Info status); `SaXML_Profile` (schema 1.28.0: `saxml22` | `saxml23`, derived by the driver from `FMSaveAsXML/@version`)
- **ExternalDataSourceCatalog** — External data sources
- **DataSourceFileMap** — Derived (P4): per `(File_Name, DS_UUID)` the **imported** file a FileMaker data source resolves to (`Resolved_File`) — direct `DS_Name` match first, then the `Path` list in FileMaker search order (protocol prefixes and directories stripped, case-insensitive; closes the `_dev`-suffix gap where the declared name and the imported file name differ). Data sources without an imported match have no row (partial corpus). Used by the P4 clone scoping (base_table block, prefer-declared-source pass) and the P6 view `v_check_phantom_links`
- **BaseTableCatalog** — Base tables of the FileMaker solution; `BT_Comment` = the table comment from Manage Database (schema 1.30.0, both SaXML profiles; empty → NULL)
- **TableOccurrenceCatalog** — Table occurrences in the relationship graph
- **RelationshipCatalog** — Relationships between table occurrences (per predicate, column `Predicate_Index`). `Rel_UUID` = native FileMaker UUID of the relationship (repeated on every predicate row; = `ObjectCatalog.Object_UUID`, schema 1.34.0), plus raw change metadata `Modified_At` / `Modified_By` / `Modified_Account` / `Modifications`
- **v_table_occurrence_usage** — MATERIALIZED analysis table (schema 1.38.0, `create_analysis_views.sql`): one row per usage of a table occurrence — `TO_UUID`, `TO_Name`, `File_Name`, `Category`, `Role`, `User_UUID/_Type/_Name/_File`, `Container_UUID/_Type/_Name` (layout of a LayoutObject user), `Ref_Count`, `Is_Edge` (the usage also exists as an ObjectLinks edge). Categories: `layout_context`, `portal`, `navigation`, `relationship`, `relationship_cascade` (both sides of a relationship with cascade delete), `lookup`, `lookup_context`, `value_list` (source TO + secondary field), `value_list_related`, `calculation` (`TO::Field` in any formula), `calculation_text` (files **without** DDR info only: `TO::Field` found in `CalculationsCatalog.Formula_Text`, one row per occurrence — a TO name directly before `::`, left-delimited by the text start or a non-name character; against files with DDR info it finds about 95 % of the (file, TO) pairs, false hits count as usage, unqualified field names and evaluation contexts stay invisible), `script_step`, `layout_field`, `table_view`, `layout_part` (break field), `security` (record-access context), `calc_context` (evaluation context of a formula). **Where-used for a TO must read this table, not only ObjectLinks:** a `TO::Field` reference creates an edge to the field, never to the TO. TOs are resolved per file via `(File_Name, TO_ID)` where the source carries the ID (heal- and clone-safe). Resolved formula references and contexts need DDR info; dynamic references (`GetField`, `Evaluate`, names inside SQL strings) are invisible
- **v_table_occurrence_class** — MATERIALIZED (schema 1.38.0): one row per TO with `Usage_Class` (`unused` · `used` · `relationship_bridge` · `dead_branch` · `dead_island`), `Reason` (`path` = intermediate TO on the relationship path between two used TOs, e.g. the join TO of an n:m relationship; `cascade_delete`), `Ref_Count`, `Usage_Ref_Count` (without relationship sides), `User_Count`, `Relationship_Count`, `Text_Ref_Count` (usages of category `calculation_text`), `Used_Branches`, `Dead_Group_ID`/`Dead_Group_Size` (connected dead subtree, cleaned up together), `Anchor_TO_UUID/_Name` (the live TO a dead branch hangs on), `Low_Confidence` (file without DDR info — there `unused`/`dead_*` are **unverified**, a usage may be invisible; `used`/`relationship_bridge` rest on found usages and hold). Path analysis relies on the relationship graph being a forest (FileMaker forbids cycles): a TO without own usage is needed iff at least two of its branches contain a used TO. Conservative — an intermediate TO counts as needed even if no concrete reference walks that path; `dead_*` means "no statically visible path", a review candidate, not a delete recommendation
- **v_object_usage** — MATERIALIZED (schema 1.40.0, `create_analysis_views.sql`): one row per object of the types Field, Script, Layout, CustomFunction, ValueList, BaseTable, ExternalDataSource, PrivilegeSet, TableOccurrence, Relationship — **the** usage definition shared by the `unused_*` rules (test `unused-code`), the usage dashboard and the search. Usage = incoming `ObjectLinks` edge (`Target_UUID` + `Target_File`) whose role has `LinkRoleRegistry.Counts_For_Where_Used`, except where the per-type override in the same SQL file applies (BaseTable: only `base_table` — `parent_table` carries the flag but is containment). The aggregate edge Layout → Field (`displays_field` without subrole, see the link roles below) is excluded — it duplicates the layout-object edges; excluding it changes `Usage_Refs`/`Usage_Users` only, never `Usage_Owners` or the class. Columns: `Object_UUID`, `Object_Type`, `Object_Name`, `File_Name`, `Usage_Owners` (distinct using **containers** — a LayoutObject or LayoutPart counts as its layout; the number to show as "usage"), `Usage_Users` (distinct source objects), `Usage_Refs` (references — counting incoming edges; the references tab sums its rows' ×N to the same number), `Usage_Roles` (list), `Usage_Files` (distinct source files), `Cross_File`, `Entry_Point` (script in the Scripts menu / layout in the layout menu, `Is_Hidden = FALSE`, regardless of usage), `Key_Field` (field is `left_field`/`right_field` of a relationship), `Low_Confidence` (file without DDR info, only for the formula-dependent types Field/Script/Layout/CustomFunction/ValueList plus TO and Relationship), `Usage_Class` — `used` · `unused` · `entry_point` (no usage, but in a menu) · `builtin` (no usage, built-in privilege set ID 1–3); TableOccurrence rows take counts and class from `v_table_occurrence_usage`/`_class` (classes `relationship_bridge`/`dead_branch`/`dead_island` included); Relationship rows have no counts (NULL) and the class `dead_island`/`dead_branch` when one of their TOs has it, else `used`. No threshold in the view — "rarely used" is `Usage_Owners <= n` in the consumer. Dynamic references stay invisible
- **FieldsForTables** — Fields of all tables with type, properties and AutoEnter details (Lookup, Calculated, ConstantData); FileMaker 26 exports (schema 1.28.0): `Field_Annotation`, `Field_DisplayNames_Enabled`, `DisplayNames_Calc_Text`/`DisplayNames_Calc_Hash` (NULL for FileMaker ≤ 22)
- **CustomFunctionsCatalog** — Custom functions
- **CalcsForCustomFunctions** — Formulas of the custom functions
- **ScriptCatalog** — All scripts, folders and separators; the change metadata is in `Modified_By` / `Modified_At` / `Modified_Account` / `Modifications` (the compatibility copies `Last_Modified_By` / `Last_Modified_At` were removed with schema 1.36.0)
- **StepsForScripts** — Script steps with parameters. `Boolean_Type`/`Boolean_Value` = the step's **first** `<Boolean>` option in document order — a positional pick: SaXML 2.3.0.0 (FileMaker 26) reorders and extends the boolean options of some steps (e.g. *Save Records as PDF*: "With dialog" before "Append to existing PDF", plus "Create folders"), so the same step reads differently across export versions; every option is in `Parameters_XML`. Note `Calculation_Text` = the step's **first** calculation in document order, excluding repetition/window-geometry (`Bounds`) slots — NULL when the step carries only such slots (e.g. a `New Window` without a name). For every calculation of a multi-calc step use **StepCalculations**. `Opens_Window` (derived, P3): TRUE/FALSE for the two window-capable steps only (`New Window` = always TRUE, `Go to Related Record` = TRUE iff its "New window" option is set), NULL for all other steps. A **collapsed block** (a folded `If`/`Loop`, or a folded disabled step) surfaces through the same positional pick: `Boolean_Type='Collapsed'`, `Boolean_Value='True'` (SaXML `<Boolean type="Collapsed" id="33554432">`, written by both profiles) — editor state, not behaviour, and not part of the clipboard form the generator emits
- **StepCalculations** — One row per positioned calculation of a step (derived in P3 from `Step_XML`): `Slot` (parent element of the calculation — `Name`, `height`, `URL`, `Title`, `value`, `repetition`, … or `Parameter:<type>` when directly under a `<Parameter>`), `Calc_Position` (the `@position` attribute — NOT step-unique, FileMaker restarts numbering in some parameter containers), `Slot_Seq` (1-based ordinal within one slot parent, e.g. JavaScript argument lists), `Calc_Text`. Covers what `Calculation_Text` cannot: window names vs. geometry, dialog title vs. message, URL vs. cURL options
- **Layouts** — Layouts of the solution
- **LayoutObjects** — All layout objects across all layouts (22 types, real container hierarchy via direct child axes; corpus reaches nesting depth 5); `Part_Seq`/`Part_Kind` name the layout part each object belongs to (schema 1.39.0, see the structure section)
- **LayoutParts** — Layout sections (Header, Body, Footer, Sub-summaries; one row per part via `Part_Seq` — multiple sub-summaries of the same kind stay distinct; `Break_Field_*`/`Break_TO_*` = sub-summary break field; a `Break_Field_UUID` missing from `FieldsForTables` is rewritten in P4 to the canonical field UUID via `Break_TO_UUID` + `Break_Field_ID`). `Part_Type` is canonical English (localized names mapped in P4; `Part_Kind = 5` is always `Trailing Sub-summary` since schema 1.29.0 — FileMaker ≤ 22 exports it mislabeled as "Trailing Grand Summary", FileMaker 26 correctly; the raw `@type` stays in `Definition_Type`); `Part_Kind` is the locale-independent code. Part definition (schema 1.39.0): `Part_Name` (FileMaker-generated `/Part/@name`, sub-summaries only, e.g. `Sub-summary by Text1 (Leading)`), `Part_Break_Every` (n of the dialog option "page break after every n occurrences", `Definition/@restartEachGroup` — present only when that option is set), `Part_LocalCSS_Name` (named part style, NULL = none), `Part_LocalCSS_Type` (FileMaker 26 only — FileMaker 22 writes no `@type`, so detect a style by `Part_LocalCSS_Name`), `Part_LocalCSS` (raw CSS), `Part_Alt_Row_Local` / `Part_Active_Row_Local` (row-state values set **locally** on a body part, NULL = not set locally or not a body part). The dialog options O1–O5 are bits of `Part_Options` (bit 0 page break before each occurrence, bit 1 page break after every n, bit 2 restart page numbers, bit 6 allow part to break across page boundaries, bit 8 discard remainder of part; bits 7/10 are no dialog options). Alternate/active row state are CSS, not bits — effective value = cascade local → named part style → theme `body` rule (both in **ThemePartStyles**) → off (Classic: off)
- **LayoutTableViewColumns** — Columns of a layout's table view (schema 1.28.0, FileMaker 26 exports only — SaXML ≤ 2.2.x does not serialize them): one row per (layout, column) with `Column_Seq`, `Column_ID/Name`, `Is_Hidden`, `Column_Width` and the field reference (`Field_ID/Name/UUID/Repetition`, `TO_*`). Not layout objects (no bounds, no own UUID); P4 derives Layout → Field `displays_field` links with subrole `table_view_column`. Check view `v_check_table_view_columns`
- **LayoutObjectConditions** — Conditional-formatting rules, one row per rule (schema 1.25.0, derived in P3 from `Object_XML`, **depth-anchored** at `/LayoutObject/Conditions/Formatting/Condition` — own rules only, container nesting cannot double-count; use this table for ANY CF question instead of regexing `Object_XML`). Columns: `Rule_UUID` (synthetic md5), `Object_UUID` (owning layout object), `Layout_ID`, `Rule_Index` (1-based serialization order = FileMaker dialog order = `Condition/@id`+1 = DDR suffix `Condition_N`), `Condition_Type` (raw `@type`, fixture-verified: 0 = formula, 1 between, 2 not between, 3 equal, 4 not equal, 5 greater, 6 less, 7 greater/equal, 8 less/equal, 9 contains, 10 does not contain, 11 begins with, 12 ends with, 13 empty — a "not empty" operator does not exist), `Condition_Kind` (`formula`/`value`), `Options_Raw` (format-selection bitmask, raw; **bit0 = rule ENABLED** — 0 means the rule is disabled in the dialog, so `aktiv = Options_Raw & 1`; bit1 text color, bit2 fill color, bit4 "more formatting", bit7 icon color; the text-style toggles bold/italic/underline/strikethrough set NO bit and materialize only in `Local_CSS`), `Calc_Text` (condition formula — **also filled for value rules**: FileMaker serializes the equivalent `Self` formula), `Calc_Hash` (DDRREF, NULL without DDR-Info), `Calculation_UUID` (FK → CalculationsCatalog role `conditional_format`, filled in P4 via owner + `Condition_<Rule_Index>`; NULL for rules without an instance — value rules with an EMPTY chunk list (`Calc_Hash` = `upper(md5(''))`, FileMaker writes no chunks), no-DDR files, and the rules of a UUID-healing survivor whose own DDRREF has `hash=""` (FileMaker wrote that anchor's chunk list for a pasted twin — the instance belongs to the twin, see CalculationsCatalog owner resolution); a set FK always points to an instance with the same hash), `Range_Start`/`Range_End` (value-rule operands as raw expression text — numbers, quoted strings, variables; FM pre-encoding decoded; a leftover `Range` can survive an operator switch on a type-0 rule — `@type` is authoritative for the kind, never `Range` presence), `Formatting_Membercount` (`@membercount` of the own Formatting block, P6 anti-nesting guard `v_check_cf_rules` — the same view also counts `calc_without_rule_n`, `hash_without_fk_n` (empty chunk lists excluded), `empty_chunklist_n` and `fk_hash_mismatch_n`; all expected 0 except `empty_chunklist_n`), `Local_CSS` (applied format as raw CSS, parsing is API/frontend territory; includes dialog defaults such as `background-color`/`color` even when not actively chosen — the Options bits tell what was selected). Carrier types: leaf-ish objects plus Panels and Button-Bar segments; **Group and Portal never persist own CF** (a rule applied there is dropped on save — fixture-verified), so their `Object_XML` CF matches are always nested children
- **FieldDisplayNames** — JSON elements of a field's display-names formula (schema 1.29.0, derived in P3 from `FieldsForTables.DisplayNames_Calc_Text`; FileMaker 26 "customize field display names"): one row per element of `JSONSetElement ( "{}" ; [ "<key>" ; <label or formula> ; JSON<Type> ] ; … )` — `Element_Seq`, `Element_Key`, `Value_Text` (label unquoted, or the raw expression), `Value_Kind` (`literal` | `formula`), `Json_Type`. Formulas not in that shape yield no rows (the raw formula stays in `FieldsForTables`). Inventory only, no edges — the formula's references run through the `display_names` calculation instance
- **LayoutObjectSymbols** — Inventory of `{{…}}` symbols in text objects and button labels (schema 1.27.0, derived in P3 from `Text_Content`; `{{CurrentDate}}`, `{{FoundCount}}`, … — semantically the result of `Get(X)` at display time). One row per (layout object × symbol): `Object_UUID`, `Layout_ID`, `Symbol_Text` (as typed), `Symbol_Norm` (lowercased grouping key — symbols are case-insensitively typable), `Occurrence_Count`. Since converter 2.28.0 a **valid** symbol also carries a where-used edge `displays_symbol` to the BuiltinFunction `Get(<Symbol>)` it displays (see the link-role list) — "which layouts show {{PageNumber}}?" is an ordinary where-used query on that target. An **invalid** symbol deliberately stays edgeless: it names no Get parameter, renders literally at runtime and must not invent a catalog object; the analysis test `layout-merge-anchors` (rule `layout_invalid_symbol`) is where it becomes visible. The table stays the inventory for everything else — occurrence counts, the typed spelling, and the invalid symbols themselves. `Is_Evaluated` (schema 1.33.0): TRUE for a text object (kind 2), FALSE for the label of a button (kind 10) or popover button (kind 14) — FileMaker never evaluates a symbol there, not even a valid Get parameter; such a symbol gets no `displays_symbol` edge and registers no BuiltinFunction node, and the rule `layout_button_label_symbol` (test `layout-merge-anchors`) reports it. Filter on `Is_Evaluated` for "symbols that display a value"
- **ValueListCatalog** — Value lists
- **OptionsForValueLists** — Details of value lists (CustomValues, field references, External source: `External_DS_*`/`External_VL_*` columns for value lists sourced from another file; schema 1.38.0: `ShowRelated` + `ShowRelated_TO_ID/_Name/_UUID` — the start TO of „include only related values starting from“, the TO from which FileMaker walks the relationship graph to the source TO; `ShowRelated` FALSE = all values, TO columns NULL)
- **AccountsCatalog** — User accounts
- **PrivilegeSetsCatalog** — Privilege sets
- **PrivilegeSetRecordAccess** — Custom Record Privileges, table level (per Privilege Set × table × operation View/Edit/Create/Delete; access mode, calc text/hash, evaluation context)
- **PrivilegeSetFieldAccess** — Custom Record Privileges, field level (per Privilege Set × table × field; per-field access mode, only for tables with `Fields access="Custom"`)
- **PrivilegeSetObjectAccess** — Custom Privileges for Layouts/ValueLists/Scripts (per Privilege Set × object; per-object access mode, Layout records-access, class create flag)
- **DDR_ScriptSteps** — Human-readable script steps (optional, only when DDR-Info is available)
- **DDR_Calculations** — Formula chunks for dependency analysis (optional, only when DDR-Info is available). `Chunk_Type` is canonicalized once after extraction (phase 1c): FileMaker's **design functions** (`WindowNames`/`Fensternamen`, `DatabaseNames`, `LayoutIDs`, `ValueListItems`, …) arrive as `PluginFunctionRef` — the chunk type otherwise used for plug-in calls — and are re-typed to `FunctionRef` by a positive name match against `DesignFunctionNames` (the `type` attribute inside `Chunk_Content` is rewritten too, the token text stays as exported); every other chunk keeps its exported type
- **DesignFunctionNames** — Solution-independent name list of **every FileMaker built-in function** (all reference categories except the Get selectors; converter 2.24.0 — before: design functions only, hence the table name) in every reference language (`Function_ID`, `Canonical_Name`, `Category`, `Language`, `Name`, `Name_XML` = the `&#xHH;` char-ref form of non-ASCII names as the DOM chunk path serializes them; NULL when identical). Rebuilt on every import by the generated seed `ingestion/sql/generated/design_functions_seed.sql` (derived from `reference/fm_spec.duckdb` by `ingestion/gen_design_functions.sh`). The positive match list of the phase-1c chunk retype and of `v_check_design_function_retype`; not an object catalog — never joins into ObjectCatalog/ObjectLinks
- **BuiltinFunctionIdentity** — Reference identity of every **resolved** BuiltinFunction node (schema 1.32.0, built in P4): `Object_UUID` (PK), `Function_ID` (reference `functions.function_id`), `Canonical_Name`, `Namespace` (`function` | `getparameter`). Written by the import, **never** recomputed from the name — consumers look the reference up instead of carrying the identity rule (the docset reference pill joins `Function_ID`, the token links resolve the UUID). `Function_ID` is a join key **within one import**, not the identity key: identity is `Canonical_Name`, because the reference declares that its stable lookup key while `function_id` is a plain PK without a stability promise. A node with a name fallback deliberately has **no row** — absence is the statement "not resolvable", queryable per anti-join: `SELECT Object_Name FROM ObjectCatalog oc WHERE oc.Object_Type='BuiltinFunction' AND oc.Object_UUID NOT IN (SELECT Object_UUID FROM BuiltinFunctionIdentity)`
- **BuiltinTokenResolution** — How each *token form* occurring in the calculations resolved (schema 1.32.0, built in P4): `Token_Key` (the identity string a token had **before** the normalization — `'Get::<Sub>'` or the bare token, which is what makes the table the ALT → NEU map), `Object_UUID`/`Object_Name` of the node it resolves to, plus `Canonical_Name`, `Function_ID`, `Namespace` (all three NULL = name fallback). One row per token form, not per occurrence. The single place the **namespace-aware** rule is expressed (a `Get` sub-parameter resolves only in the parameter namespace; a free token prefers the function namespace and falls back to the parameter namespace), which all P4 call sites consume by join — including the persistent view `v_calculation_links`, which is why the table is persistent rather than session-local. Useful after the fact to see *how* a given token resolved
- **v_builtin_token_lookup** — VIEW (P4, schema 1.32.0): `<token name> → BuiltinFunction node`, the one lookup surface for consumers that know a built-in only by name (a formula token, a layout symbol, a docset entry). Key is `Name_Norm` = `lower(<name>)`, guaranteed unique per node; columns `Name_Decoded`, `Object_UUID`, `Function_ID`, `Canonical_Name`, `Namespace` (the last three NULL for a name-fallback node). It covers **every reference language and both namespaces** with the same precedence the import uses, plus the raw names of the fallback nodes — so no consumer has to rebuild the identity rule. Consumers today: the object search (a built-in is findable under every localized spelling, `Matched_Values` names the one that hit), the token cross-navigation of every calculation view, and the script reference list. Two text axes per name, because there are two consumer classes: the decoded spelling (catalog/reference) and the **entity-encoded** one (`AnzahlGefundeneDatens&#xE4;tze` — the form FileMaker's DOM path writes into `DDR_Calculations.Chunk_Content`); `Name_Decoded` hands a raw-text consumer the readable spelling back. Collision-free because no function name contains an entity reference
- **GetParameterNames** — Solution-independent name list of the **bare `Get(…)` parameters** (converter 2.28.0): `Function_ID`, `Canonical_Name` (English), `Source` (the reference lookup axis), `Name` (canonical English *or* a localized spelling — FileMaker accepts and renders both as a layout symbol). Second table of the same generated seed `ingestion/sql/generated/design_functions_seed.sql`, rebuilt on every import. The validity gate of the `displays_symbol` edge and of the `BuiltinFunction` targets registered from symbols; deliberately NOT part of `DesignFunctionNames` (Get selectors reach the chunk stream only as `FunctionRef` inside `Get(…)`, never as `PluginFunctionRef`). Not an object catalog. Caveat for consumers: the localized coverage is uneven — Spanish and Portuguese parameter names are absent, German only partly covered — so "not in this table" is a strong hint, not a proof
- **DDR_ChunkListContexts** — One row per ChunkList anchor of the DDR_INFO part (schema 1.27.0), **including empty ChunkLists** (`Chunk_Count = 0` — those leave no row in DDR_Calculations because they have no chunks; FileMaker writes them for typed layout calculations with an expression, losing all references). Carries the anchor's context TO (`Context_TO_ID/Name/UUID` — the direct `TableOccurrenceReference` child next to the `ChunkList`). Join anchors ALWAYS via `Calc_UUID` (anchor name `_<Owner-UUID>_<Slot>`), never via `Calc_Hash`: identical formulas share the hash but each anchor carries its own context TO. Consumers: field-name resolution against the context TO (P2), display-calculation enrichment + empty-ChunkList fallback instances (P4), `v_check_display_empty_chunklist` (P6)
- **DDR_DisplayCalcAnchors23** — Staging of the `DisplayCalculations` anchors of `saxml23` files (schema 1.28.0): FileMaker 26 pads the list of every layout object with a layout calculation in its text (text objects, button labels) to 12 anchors. One row per chunk (`Chunk_Index ≥ 1`) plus a context row per anchor (`Chunk_Index = 0`: `Chunk_Count`, `Context_TO_*`), `Slot_Index` from the anchor name, `Promoted` = copied into `DDR_Calculations`/`DDR_ChunkListContexts` by stage P1d (only slots below the `<<ƒ:…>>` token count of the object's `Text_Content`). Unpromoted rows = the padding, kept visible (`v_check_saxml_profile`). Always empty for `saxml22` files
- **PasteIndexList** — List of object IDs for copy/paste operations
- **BaseDirectoryCatalog** — Base directory of the FileMaker file
- **ScriptTriggers** — Script triggers on all three owner levels (`Owner_Type` = `File`/`Layout`/`LayoutObject`; e.g. OnFirstWindowOpen, OnRecordLoad, OnObjectSave). `Trigger_Action` is a generic passthrough of the SaXML `action` attribute (no enum). Mode scope (schema 1.24.0): `Trigger_BrowseMode`/`Trigger_FindMode`/`Trigger_PreviewMode` — SaXML writes only ACTIVATED modes as attributes, so NULL means "mode off", never "unknown". `Trigger_ScriptParameter_FieldName` (1.24.0, OnWindowTransaction only): name-only field reference whose content FileMaker adds to the JSON script parameter — late-bound per triggering table; resolved since 1.26.0 as name-CANDIDATE edges `reads_field · transaction_parameter_field` (one edge per same-named field of the OWN file — a deterministic 1:1 edge is impossible by design; an orphaned name after a field rename is a legitimate state, reported by P6 `v_report_trigger_parameter_fields`, deliberately no FAIL gate). `Trigger_Parameter_Text` (1.26.0): structural plain text of the trigger's parameter calculation (`ScriptReference/Calculation/Text`, CDATA-decoded; all three owner levels) — P4 feeds it into `Formula_Text` of the `script_trigger_parameter` instances (DDR anchors AND a per-trigger no-DDR fallback with `Calc_Kind_Raw='ScriptTrigger_<id>'`, replacing the former collapsed one-instance-per-object fallback), so trigger parameters are visible without DDR-Info too. File-level triggers have no script parameter (the FileMaker dialog offers none); `Trigger_XML` is populated only for Layout/File owners
- **ExtendedPrivilegesCatalog** — Extended privileges (fmwebdirect, fmxdbc, fmapp, etc.); `PrivilegeSet_IDs` / `PrivilegeSet_Names` = the granting sets, position-aligned, `[]` = granted to no set (never NULL, never a NULL element — P6 `v_check_reference_lists`)
- **CustomMenuCatalog** — Custom menus with nested hierarchy
- **CustomMenuItemCatalog** — Individual menu items (from Menu_XML: commands, submenu/separator flags)
- **CustomMenuSetCatalog** — Menu sets with member-menu ID lists (`Member_Menu_IDs` / `Member_Menu_Names`, `[]` = no member menu)
- **ThemeCatalog** — CSS rule sets for layouts
- **ThemePartStyles** — Row-state defaults of the themes (schema 1.39.0, derived in P3 from `ThemeCatalog.Theme_XML`): one row per (`Theme_UUID`, `File_Name`, `Style_Name`) with `Theme_Name`, `Style_Name` = `body` (theme default of the body part, rule `body:normal .self`) or the part-style name (rule `part.<name>:normal .self`), `Alt_Background` (`-fm-body-alt-background`) and `Active_Row_Style` (`-fm-use-body-current-row-style`), NULL = not set in that rule. Stages 2 and 3 of the row-state cascade (see LayoutParts); Classic themes have no row → off
- **FileOptionsCatalog** — File options from the Metadata branch: encryption status, minimum version, **auto-login account (security-relevant)**, sharing visibility, default/start layout (→ `default_layout` link). Exactly one row per imported file — P6 `v_check_file_options_coverage` lists files without one (warn, re-import)
- **FileAccessAuthorizations** — Inter-file access authorizations
- **LibraryReferences** — Library references (metadata only, blobs discarded)
- **LinkRoleRegistry** — Link-role classification per role: columns `Link_Role`, `Link_Kind` (`usage`/`containment`/`restriction`), `Counts_For_Where_Used` (boolean). No prose/`Description` column — the meaning of each role is the "Link roles" list below. P6 warns when an ObjectLinks role lacks a registry entry
- **ScriptStepRoleMap** — Curated Step_ID → Link_Role mapping for Script→Field links (locale-independent; `Step/@name` is localized in SaXML exports). Canonical_Name documents the English reference name; IDs verified against the reference index `reference/fm_spec.duckdb` (`script_steps.step_id` ≙ SaXML `Step/@id`), which is deliberately NOT a runtime dependency of the converter Converter 2.24.0 adds 221/144/245 (`sets_field`), 219/246 (`reads_field`), 240/242/244 (`references_field`) and moves 132 Export Field Contents to `exports_from_field`.
- **FilesCatalog** — Metadata of all imported FileMaker files (multi-file support); `SaXML_Version` (root `@version`, e.g. `2.2.3.0`/`2.3.0.0`) and `SaXML_Profile` (`saxml22` | `saxml23`) since schema 1.28.0
- **ObjectCatalog** — Central object registry covering all 25+ object types across all files
- **ObjectLinks** — Links between objects (operational & structural, including cross-file links)
- **VariableUsages** — Every individual variable usage with its context (script, field, layout)
- **VariablesCatalog** — Aggregated overview per variable (set/read counts, scope, files)
- **CalculationsCatalog** — One row per calculation **instance** (schema 1.22.0; successor/superset of the former `v_calc_anchors` build). Identity = Owner × `Calc_Role` × `Calc_Index` (synthetic `Calculation_UUID`, type-tagged md5 — a formula HASH is a property, never the identity: SaXML dedupes chunk lists by content, one hash can serve tens of thousands of instances). Union of the DDR anchors (`DDR_Calc_UUID`, hash/chunk aggregates, `Display_Text`) and the structural slots without a DDR anchor (field validation/message slots, `StepCalculations`, CF bodies, LayoutObject text slots, record-access calcs) — instances exist **also without DDR-Info** (`Formula_Hash`/`Chunk_Count`/… are enrichment, may be NULL). Key columns: `Owner_UUID/Type/Name`, `Calc_Role` (normalized slot vocabulary: `field_calculation`, `auto_enter`, `validation`, `validation_message`, `container_path`, `custom_function`, `step_parameter`, `step_xslt`, `record_access`, `hide`, `field_entry` (schema 1.31.0, field-entry formula), `tooltip`, `conditional_format`, `popover_title`, `panel_title`, `active_segment` (schema 1.37.0, DDR suffix `ButtonBar` = the button bar's "Active Segment → Specify" formula at `/LayoutObject/ButtonBar/Select/Calculation/Text` (`ButtonBar/Options` = 2), returns the segment's object name; converter 2.42.0: `Formula_Text` read P4-locally from the bar's own `Object_XML`, plus a structural instance without hash for files without DDR-Info; a fixed or no active segment (`<Select><id>`) has no instance; the bar's edges carry `Link_Subrole = 'ButtonBar'`, the formulas of its segments stay on the segments), `script_trigger_parameter`, `menu_install`, …; an unknown suffix falls back to `lower(raw)` and is reported by P6 `v_check_calc_roles`), `Calc_Kind_Raw` (raw DDR suffix), `Calc_Index` (1-based per owner × role, document/position order), `Edge_Subrole` (the `Link_Subrole` the owner-projected edges of this instance carry — join key of `v_calculation_links`), `Formula_Text` (structural plaintext), `Display_Text` (chunk-reconstructed), `Result_Type` (schema 1.27.0, `display_calculation` only: result type from the `%X:` prefix of the merge syntax — `Text` (no prefix, the default), `Number` (`%N:`), `Date` (`%D:`), `Time` (`%I:`), `Timestamp` (`%M:`); unknown prefixes stay raw as `%<X>`; NULL for every other role), `Source_Path` (structural origin). Registered in ObjectCatalog as `Object_Type='Calculation'`; owner containment via the structural `has_calculation` link. **`display_calculation` instances** (schema 1.27.0): `Formula_Text` carries the localized raw formula from the owner's `Text_Content` (i-th `<<ƒ:…>>` occurrence, wrapper + `%X:` prefix stripped) and `Context_TO_UUID/Name` come from `DDR_ChunkListContexts`; typed layout calculations with an EMPTY DDR ChunkList (FileMaker defect) get a fallback instance (`Formula_Hash` = md5 of the empty string, `Display_Text` NULL) plus recovered references matched from the formula text: `reads_field` against the context TO's field names (on a field↔CF name collision the field must appear `${…}`-quoted — FileMaker serializes it that way; unquoted means the CF), `calls_customfunction` against the file's CF names (locale-independent, unlike builtins) and `reads_variable` via the `$`-syntax (string literals stripped) — only BUILTIN function references remain unresolved (localized names). A `%X:`-prefixed chunk whose remainder starts with `$` is a REAL variable behind the result type (`<<ƒ:%N:$$var>>`) and keeps its usage with the prefix stripped. **Button labels** (schema 1.33.0): a `<<ƒ:…>>` typed into the label of a button or popover button with a DDR anchor runs through the same path (`DisplayCalculations_<i>`; P1d promotes it because the token count reads `Text_Content`). FileMaker does not always write that anchor (when it does is not fully pinned down — mixed labels can carry one or not), and a file exported without DDR-Info has none at all — then the instance has `Calc_Kind_Raw` = `Edge_Subrole` = `LabelText_<i>` (i = token index as with `DisplayCalculations_<i>`), `DDR_Calc_UUID` NULL, the layout's TO as context, and its references are matched from the formula text with that subrole (fields of the layout TO or qualified `TO::Field`, custom functions, variables; builtins stay unresolved). Fields of an EXTERNAL TO (converter 2.34.0) are matched in P4 Phase A against the imported home file of the TO's base table (`Is_Cross_File` = TRUE). `popover_title` / `panel_title` instances carry `Formula_Text` from `LayoutObjects.Title_Calculation_Text` and exist without DDR-Info too (schema 1.33.0). Field slot `5` (FileMaker 26 display-names formula) = role `display_names`; the FileMaker 26 validation anchor `_4_2` is folded to slot `2` = `validation` (schema 1.28.0). `Is_Enabled` (schema 1.29.0): FALSE for the instance of a disabled field slot (FileMaker 26 `enable="False"`) — the instance stays, its operational links are suppressed. **Owner resolution of DDR anchors** (schema 1.37.0): normally the object whose UUID the anchor name `_<UUID>_<Suffix>` carries. Copies with the same UUID (pasted layout objects, steps of a duplicated script) share their anchor names; FileMaker writes ONE chunk list per name, and only the copy that owns it carries `DDRREF hash="<H>"` in its own XML (the others `hash=""`). For anchors of a UUID-healing group (census `DuplicateAbsorptionDetails`, catalogs `LayoutObjects`/`StepsForScripts`) the owner is therefore the group member whose own `Object_XML`/`Parameters_XML` carries anchor name AND hash — the same attribution P2 uses for the edges, so instance and edges agree (ambiguous → survivor). A survivor whose own DDRREF is `hash=""` has no chunks for that formula: no DDR instance, no references (source limit); its hide/tooltip/… text slots keep a structural instance without hash. P6 `v_check_calc_owner_hash` lists DDR-anchored LayoutObject/ScriptStep instances whose hash is missing from the owner's own XML (expected empty; baseline without healing 0). Never re-derive the owner from the UUID inside `DDR_Calc_UUID` — join on `Owner_UUID`.
- **v_calculation_links** — VIEW (P4): Calculation → target, **derived** from the canonical owner-projected usage edges (variant A — no physical duplicate edges, no where-used double counting). Non-step owners resolve via ObjectLinks (`Link_Subrole` ↔ `Edge_Subrole`, role whitelist `reads_field`/`validates_by_calc`/`calls_customfunction`/`calls_function`/`calls_pluginfunction`); ScriptStep owners resolve instance-exactly via `XMLCalcReferences`/`PluginFunctionUsages` (`Source_Subkey` = step index — the ObjectLinks anchor is the script and would be ambiguous). Known limits: variable targets missing (live in VariableUsages), `calls_script` via MBS:FM.RunScript missing
- **DuplicateAbsorptions** — Dup-absorption census (monitoring): parsed source-record counts per catalog × file × chunk, written in P1. The P6 view `v_check_absorbed_dups` compares against live row counts — a positive difference means the per-file upsert silently collapsed duplicate-UUID source objects (export defect); reported as a warn finding in the import report. The opposite direction is P6 `v_check_census_integrity`: more stored rows than census records, or no census row for a catalog with rows, means the census was lost after P1 (warn, re-import the file)
- **DuplicateAbsorptionDetails** — per-occurrence details of colliding intra-file duplicate UUIDs (type, name, container context, plaintext, payload). Schema 1.19.0 adds the UUID-healing mapping: `Healed_UUID` (deterministic md5 replacement UUID a twin received in the catalog, NULL = kept original / absorbed), `Heal_Status` (`kept-original` | `healed` | `absorbed`) and `Discriminator` (the internal FM id the replacement UUID is derived from) — the census is the bidirectional original↔replacement lookup layer. P4 also reads it to attribute DDR formula anchors (named after the ORIGINAL UUID) to the twin whose own XML carries them (CalculationsCatalog owner resolution). Discriminator formats per catalog: `script_id=N` (ScriptCatalog), `layout_id=N` (Layouts), `to_id=N`, `vl_id=N`, `cf_id=N`, `account_id=N`, `ds_id=N`, `table_id=N` (BaseTable), `table_id=N·field_id=M` (Fields), `script_id=N·step_index=M` (script steps — position-stable only), `layout_id=N·object_id=M` (layout objects). Rows with `Chunk_Seq = -1` were derived at the turbo merge point (duplicate pair split across sub-chunk windows — no chunk-local census exists for those). Replacement UUIDs are 32-char md5 hex WITHOUT dashes → distinguishable from native 8-4-4-4-12 UUIDs by format; `Heal_Status = 'absorbed'` remains only for double serialization (same UUID and same internal id), `FM_UUID_HEAL=0` runs and pre-1.19.0 databases
- **ObjectChangeMeta** — Change metadata per object (schema 1.35.0, bursts and mass events since 1.36.0; built in P4, rebuilt every run): one row per object **with a stamp of its own** — the `<UUID>` attributes `timestamp`/`userName`/`accountName`/`modifications`. Columns `Object_UUID`, `File_Name` (key, same identity as ObjectCatalog — P6 checks uniqueness), `Object_Type`, `Object_ID`, `Object_Name` (from ObjectCatalog), `Source_Table`, `Modified_At` (TIMESTAMP, `TRY_CAST` of the raw text — **local time of the editing client, no time zone**), `Modified_At_Raw`, `Modified_By` (FileMaker user name), `Modified_Account` (signed-in account, `''` → NULL), `Modifications` (save counter), `Author_Key` (`lower(trim(Modified_By))`), `Author_Kind` (`tool` | `runtime` | NULL = person, from the `LIKE` patterns in ChangeTechnicalAuthors), `Burst_ID` (stamps of one file with gaps ≤ 10 s), `Bulk_Event_ID` (→ ChangeBulkEvents, NULL = individual change). **Both IDs are renumbered on every run** — never persist them; a mass event is recognizable across imports by `(Scope, Start_At)`. Types: Script/Layout/CustomFunction **and their folders** (`Object_Type='Folder'`; separators and folder end markers are excluded), Field, BaseTable, TableOccurrence, Relationship, ValueList, ExternalDataSource, Account, PrivilegeSet, ExtendedPrivilege, CustomMenu, CustomMenuSet, Theme, BaseDirectory, plus `Authorization` (from FileAccessAuthorizations, no ObjectCatalog entry). **No own stamp:** ScriptStep, LayoutObject, LayoutPart, Calculation, ScriptTrigger, CustomMenuItem — inherit the container's stamp via the containment edges (`parent_script`, `parent_layout`, `parent_menu`, `trigger_owner`, `has_calculation` reversed; max. two hops Calculation → Step → Script) and present it as "container changed"; Variable and the synthetic types have none. Semantics (verified by edit experiments on FileMaker 22): the stamp is the **last** save only (earlier activity is overwritten); a paste or script import creates a new object (new UUID, `Modifications = 1`, paste time, the paster as author); a runtime password change stamps the Account with the end user; Save as Clone, Developer Utility without options and compacted copies leave every stamp unchanged. Real solutions are dominated by mass actions (thousands of objects of one file in the same minute) — **individual changes are `Bulk_Event_ID IS NULL`, developer activity additionally `Author_Kind IS NULL`**; `v_check_change_meta.bulk_pct` reports the share (`mass_minute_pct` = coarse per-minute comparison value). The account is stored as typed at login (`Admin`/`admin` for one account) — group on `Author_Key`, not on raw values. Raw columns stay at the source tables (`Modified_At`/`_By`/`_Account`, `Modifications` on every source table listed above); P6 `v_check_change_meta` (warn: `missing_objects`, `cast_failures`, `duplicate_keys`, `unassigned_bursts`; info: `future_stamps`, `mass_minute_pct`, `bulk_events`, `solution_events`, `bulk_pct`). The REST API adds the TEMP view `v_change_meta_authors` (one row per `Author_Key`: `Person_Key`, `Display_Name`, `Is_Technical`, spellings, accounts, counts) from aliases curated in the annotations sidecar (`ChangeAuthorAlias`) — it exists **only inside the API connection**; on the CLI group on `Author_Key`
- **ChangeBulkEvents** — Mass events (schema 1.36.0, P4, rebuilt every run): one action that stamps many objects at once. Detection on ObjectChangeMeta only (never on CatalogChangeMeta — there a counter rising without a new timestamp is normal): burst = stamps of one file with gaps ≤ `Burst_Gap_Seconds`; file event = burst ≥ `Mass_Min_Objects` objects or a burst written only by `tool` authors; file events of the same class (tool / non-tool) chain while each starts ≤ `Solution_Window_Seconds` after the latest end — a chain over ≥ `Solution_Min_Files` files is one event. Columns `Bulk_Event_ID`, `Scope` (`file` | `solution`), `Kind` (`tool` = only tool authors · `paste_import` = share of `Modifications = 1` ≥ `Paste_Min_Share` — pasted/imported objects start with counter 1 · `mass_action` = the rest: migrations, find & replace, default objects of a new file), `Start_At`, `End_At`, `Files`, `Objects`, `Bursts`, `Mod1_Share`, `File_Names`, `Object_Types`, `Authors` (`Author_Key` values). Times are local client time — across time zones a solution event can fall apart into file events
- **ChangeBulkConfig** — the detection parameters (schema 1.36.0, P4, one row, defaults rewritten every run): `Burst_Gap_Seconds` 10, `Mass_Min_Objects` 25, `Solution_Window_Seconds` 900, `Solution_Min_Files` 2, `Paste_Min_Share` 0.8
- **ChangeTechnicalAuthors** — authors that are not developers (schema 1.36.0, P4): `Author_Pattern` (`LIKE` against `Author_Key`), `Author_Kind`, `Description`. Seed: `fmdatamigration` → `tool` (FileMaker Data Migration Tool; its bursts are always a mass event), `[webdirect-%]` → `runtime` (end user via WebDirect, typically account maintenance; no mass event, no developer activity)
- **CatalogChangeMeta** — Catalog-level change stamps (schema 1.35.0, P1): the `<UUID>` child of every catalog under `Structure/AddAction` (`Catalog` = element name: `ScriptCatalog`, `LayoutCatalog`, `BaseTableCatalog`, … — 16 catalogs; LibraryCatalog has no stamp) and of every per-table `<FieldCatalog>` (`Catalog='FieldCatalog'`, `Scope_UUID` = BaseTableReference UUID; continuation blocks of large tables carry no `<UUID>` and are skipped). Columns `File_Name`, `Catalog`, `Scope_UUID`, `Scope_Key` (`COALESCE(Scope_UUID,'')`), `Chunk_Seq`, `Catalog_UUID`, `Modified_At` (TIMESTAMP), `Modified_At_Raw`, `Modified_By`, `Modified_Account`, `Modifications`, `Newest_Child_At` (P4: max `Modified_At` of the catalog's objects in ObjectChangeMeta, per base table for FieldCatalog). PK `(Catalog, File_Name, Scope_Key, Chunk_Seq)`; identity is `(Catalog, File_Name, Scope_Key)` — `Chunk_Seq` only separates import chunks. **Multi-fed** (main chunk + LayoutCatalog chunk; only the LayoutCatalog sub-chunk that carries the catalog `<UUID>` writes) — registered in the turbo merge, producer lists guarded by `tools/tests/regression/census_feeder_map.sh`. Semantics (verified): `Modifications` rises with every save of a child; the **timestamp rule differs per catalog** — ScriptCatalog moves on every script action (edit, reorder, move into folder, create), LayoutCatalog/AccountsCatalog only on structural changes (child edits raise the counter only), FieldCatalog on a field deletion, TableOccurrenceCatalog on every OK in *Manage Database* (even when only fields changed). Catalog stamp > `Newest_Child_At` = structural change after the last object edit — a reliable **deletion indicator only for FieldCatalog**, and catalog stamps typically trail the newest child by seconds (dialog commit) → compare with a tolerance (≥ 1 min)
- **XMLStepReferences / XMLLayoutReferences / XMLCalcReferences** — P2 reference extracts (volatile, rebuilt every run). Schema 1.19.0 adds `Ref_ID` (FileMaker-internal `@id` of the referenced element — the SaXML reference triple is `id`+`name`+`UUID`) and `TO_Ref_ID` (context-TO `@id`, field references only: `FieldReference/@id` is table-local, the field key is two-stage via the TO). Used by the P4 rewrite stage to disambiguate intra-file duplicate UUIDs; NULL where the source carries no reference element (variables, name-only chunk types). `XMLLayoutReferences.Ref_Source` (schema 1.33.0) marks the origin of a merge-field row: `field_list` (the structural `<FieldList>` of a text object) or `label_text` (a merge field typed into a button/popover-button label — FileMaker never writes a FieldList for buttons — resolved from `Text_Content`: one row per resolved anchor occurrence, qualified anchors via the file's TO of that name, unqualified ones via the layout's TO, base table matched by UUID); NULL for every other row. Anchors on an EXTERNAL TO (converter 2.34.0): P2 writes an OPEN row (`Ref_UUID` NULL, `Ref_Name` = typed name, `TO_Ref_ID` = the TO's `@id`), P4 Phase A resolves it to the field of the home file of the base table (cascade `BT_UUID` → data-source path lines / `DS_Name` → `BT_Name`; `Ref_ID` stays NULL — the cross-file field is excluded from the intra-file UUID healing) or deletes it when the field is missing there (the anchor renders literally). A row that stays open has no home file in the import — not verifiable, no edge, and `layout_unresolved_merge_anchor` counts it as not literal. Guard: P6 `v_check_label_anchor_external` (`unverified` = open rows, info; `open_on_local_to` / `open_with_k1_home` expected 0)
- **v_script_block_tree** — MATERIALIZED per-step control-flow nesting (built with the analysis views): for every script step its Loop and If depth (`loop_depth_before/after`, `if_depth_before/after`, `block_depth_before`, raw `if_running_depth` for unbalanced-If detection). **Use this whenever branch scope matters** (is step X inside a Loop / which If level — e.g. dead-code or window-lifecycle reasoning); never reconstruct nesting by hand from sequential `Step_Index` reads. Partition key is `(File_Name, Script_ID)` — not `Script_UUID`, which is non-unique in merge-artifact cases

### Common columns

Every table contains:
- An `ID` column (e.g. `BT_ID`, `Script_ID`, `Field_ID`)
- A `Name` column (e.g. `BT_Name`, `Script_Name`, `Field_Name`)
- A `UUID` column for unique referencing

Use UUIDs for JOINs; the row order matches the FileMaker solution; script steps additionally carry `Step_Index`.

**Change metadata columns** (schema 1.35.0): every table of an object type that carries a `<UUID>` stamp — ScriptCatalog, Layouts, CustomFunctionsCatalog, FieldsForTables, BaseTableCatalog, TableOccurrenceCatalog, RelationshipCatalog, ValueListCatalog, ExternalDataSourceCatalog, AccountsCatalog, PrivilegeSetsCatalog, ExtendedPrivilegesCatalog, CustomMenuCatalog, CustomMenuSetCatalog, ThemeCatalog, BaseDirectoryCatalog, FileAccessAuthorizations — holds the raw values `Modified_At` (VARCHAR, `YYYY-MM-DDTHH:MM:SS`), `Modified_By`, `Modified_Account` (`''` → NULL) and `Modifications`. For cross-type questions (recent changes, activity, authors) query **ObjectChangeMeta** (typed timestamp, one table) instead of a UNION over the sources. **Always qualify these four columns with a table alias when joining** two of these tables (e.g. Layouts × ThemeCatalog) — unqualified they raise "Ambiguous reference to column name".

**`Step_Index` is 0-based and gapless** (per script: `min = 0`, `max = n-1`). FileMaker's
Script Workspace and every fm-lab user-facing surface count 1-based — **always render
`Step_Index + 1` when quoting a step number to a user**, and subtract 1 when translating a
user-quoted step number back into a `Step_Index` filter. Sort/join on the raw `Step_Index`.

## FieldsForTables — column details

Base columns: Table_ID/Name/UUID, Field_ID/Name/Type, Data_Type, Field_Comment, Field_UUID, Is_Global, Max_Repetitions, DDR_Hash, Calculation_Text. Plus 13 AutoEnter columns:

**AutoEnter base attributes (all types):**
- `AutoEnter_Type` — Type: `Looked_up`, `SerialNumber`, `Calculated`, `ConstantData`, `CreationDate`, etc. (NULL for fields without AutoEnter)
- `AutoEnter_ProhibitMod` — May the user overwrite the value?

**Lookup details (only AutoEnter_Type = 'Looked_up'):**
- `Lookup_Field_Name` / `Lookup_Field_UUID` — Source field (name and UUID)
- `Lookup_TO_Name` / `Lookup_TO_UUID` — Relationship TO (name and UUID)
- `Lookup_DontCopyIfEmpty` — Do not copy empty values?
- `Lookup_NoMatchOption` — `DoNotCopy` or `ConstantData`
- `Lookup_Context_TO_ID` / `Lookup_Context_TO_Name` / `Lookup_Context_TO_UUID` — start TO of the lookup („starting with table“, `<Looked_up><Context>`, schema 1.38.0): FileMaker resolves the lookup along the relationship path from this TO to `Lookup_TO`

**AutoEnter Calculated details (only AutoEnter_Type = 'Calculated'):**
- `AE_Calc_Text` — Plain-text formula (complementary to `Calculation_Text` for true Calculated Fields)
- `AE_Calc_Hash` — DDR hash (complementary to `DDR_Hash`; JOIN with DDR_Calculations possible)
- `AE_Calc_OverwriteExisting` — Overwrite existing values?
- `AE_Calc_AlwaysEvaluate` — Re-evaluate on every change?

**Disabled definitions (FileMaker 26 exports, schema 1.29.0 — NULL for FileMaker ≤ 22 = active):**
- `AE_Calc_Enabled`, `Lookup_Enabled`, `Validation_Calc_Enabled`, `Validation_Message_Calc_Enabled` — the `enable` attribute of `<AutoEnter><Calculated>`, `<AutoEnter><Looked_up>`, `<Validation><Calculated>`, `<Validation><MessageCalc>`. FileMaker 26 exports **disabled** definitions with `enable="False"` (FileMaker ≤ 22 omits them). A disabled slot keeps its definition columns and its calculation instance (`CalculationsCatalog.Is_Enabled = FALSE`, `has_calculation` edge), but produces **no operational links** (`reads_field`/`calls_function`/`calls_customfunction`/`reads_variable`/`validates_by_calc`/`lookup_source`) and no `VariableUsages` — where-used parity with the FileMaker 22 export. Guard: `v_check_saxml_profile.dormant_operational_edges` (expected 0)

**Annotation and display names (FileMaker 26 exports, schema 1.28.0 — NULL for FileMaker ≤ 22):**
- `Field_Annotation` — free-text annotation (`<Annotation><Text>`; empty → NULL)
- `Field_DisplayNames_Enabled` — `<DisplayNames @enable>`
- `DisplayNames_Calc_Text` / `DisplayNames_Calc_Hash` — the display-names formula (plain text + DDR hash; calculation instance of role `display_names`, DDR anchor `_<Field-UUID>_5`)

**ConstantData (only AutoEnter_Type = 'ConstantData'):**
- `AE_ConstantData` — Fixed default value

**Note:** `Calculation_Text`/`DDR_Hash` apply to `fieldtype="Calculated"` (true Calculated Fields), while `AE_Calc_Text`/`AE_Calc_Hash` apply to `fieldtype="Normal"` with an AutoEnter calculation. A field never has both populated at the same time.

**Validation / storage / serial / summary columns (schema 1.5.0):**
- `Validation_Type/_AllowOverride/_NotEmpty/_Unique/_Existing` — field validation options; `Validation_VL_ID/_Name/_UUID` — validation by value list (→ `uses_valuelist` link, Subrole `validation`)
- `Storage_AutoIndex`, `Storage_Index` (`None`/`All`/`Minimal`), `Storage_StoreCalcResults` — indexing/storage options
- `Serial_Increment/_NextValue/_Generate` — serial-number details (only `AutoEnter_Type='SerialNumber'`)
- `Summary_Operation`, `Summary_Field_Name/_UUID` — summary definition (only `fieldtype='Summary'`; → `summarizes_field` link)

**Field-option coverage (schema 1.10.0):**
- `Validation_AlwaysValidate` — `<Validation @alwaysValidate>`
- `Validation_StrictType` — strict data type from `<Strict>` (`FourDigitYear`, numeric-only, time-of-day; raw token, no enum constraint)
- `Validation_MaxChars` — `<MaximumSize>` (max characters)
- `Validation_Range_From/_To` — `<Range @from/@to>`
- `Validation_Calc_Text/_Calc_Hash` — validate-by-calculation (`<Validation><Calculated>`; hash → `DDR_Calculations`, feeds the `validates_by_calc` link)
- `Validation_Message` — static custom error message (`<Message>`); `Validation_Message_Calc_Hash` — `<MessageCalc>` (message-by-calc)
- `Storage_IndexLanguage/_IndexLanguage_ID` — default index language (`<Storage><LanguageReference @name/@id>`; a **child element**, not an attribute)
- `Summary_RestartEachGroup`, `Summary_RepetitionMode` (`Together`/`Individually`) — `<SummaryInfo @restartEachGroup/@summarizeRepetition>`

**Layouts metadata columns (schema 1.5.0):** `L_TO_UUID` (context TO by UUID), `L_Width`, `L_Theme_ID/_Name/_UUID` (raw `<LayoutThemeReference>` triple), `L_Theme_Base` (schema 1.9.0, `@Base`).

**Layout theme — always read `L_Theme_Resolved_Name/_UUID` (schema 1.21.0), never the raw columns.**
SaXML encodes the **Classic theme as an empty element** `<LayoutThemeReference/>` — no `id`, `name`, `UUID` or `Base`. Only non-Classic themes carry the attribute triple, so the raw `L_Theme_*` columns are `NULL` for **every** Classic layout and the literal `'com.filemaker.theme.classic'` appears in no layout row at all. A rule that tests `L_Theme_Name = '…classic'` (or `L_Theme_Base`) therefore silently returns zero findings on a solution that is entirely Classic.

The derived columns (filled in P3, `uses_theme` links built from them in P4) resolve this:
- `L_Theme_Resolved_Name` — effective theme name, locale-independent; empty reference → `com.filemaker.theme.classic`. Display name via `ThemeCatalog.Theme_Display`.
- `L_Theme_Resolved_UUID` — effective theme UUID; for Classic taken from the file's `ThemeCatalog` **by theme name** (`Theme_ID = 1` is *not* reliably Classic), `NULL` if the file has no Classic entry.

Both are populated for real layouts only — folders (`Folder_Type` `True`/`Marker`) and separators never carry a theme and stay `NULL`. When a query must also work against catalogs older than 1.21.0, fall back to `L_Theme_Base = '…classic' OR L_Theme_Name = '…classic' OR L_Theme_ID IS NULL` (plus the folder/separator exclusion).

## LayoutObjects — structure

**Base attributes:**
- `Layout_ID` — Link to the layout (JOIN with Layouts.L_ID)
- `Part_Type` — type of the assigned layout part, canonical English as in `LayoutParts.Part_Type` (schema 1.39.0; before: raw `/Part/@type` — localized and with the FileMaker ≤ 22 kind-5 mislabel)
- `Part_Seq` / `Part_Kind` — the assigned layout part (schema 1.39.0, join `LayoutParts` on `File_Name` + `Layout_ID` + `Part_Seq`). Derived in P4: a root object (`Nesting_Level = 0`) belongs to the part whose band `[Part_Absolute, Part_Absolute + Part_Size)` contains its `Bounds_Top` (a top edge exactly on a part boundary belongs to the lower part); nested objects inherit the part of their parent — their bounds are relative to the parent and must not be mapped geometrically. NULL only for a root object outside every part (P6 `v_check_layoutobjects_without_part`, expected 0)
- `Object_ID` — Object ID (unique only within a layout)
- `Object_UUID` — Unique UUID of the object
- `Object_Type` — Type of the object (Text, Edit Box, Button, Portal, Rectangle, etc.)
- `Object_Name` — User-defined name (often empty)

**Positioning:** `Bounds_Top`, `Bounds_Left`, `Bounds_Bottom`, `Bounds_Right` — position and size in pixels

**Nesting:**
- `Parent_Object_ID` — Reference to the parent object (NULL = top-level)
- `Nesting_Level` — Nesting level (0 = top-level; nested containers reach depth 5 in practice — e.g. Tab Control → Panel → Group → Grouped Button → object)

**Calculation slots (plain text):** `Hide_Calculation_Text`, `Tooltip_Calculation_Text`, `Label_Calculation_Text`, `Title_Calculation_Text`, `ScriptTrigger_Parameter_Text`

**Text, label and title (schema 1.33.0)** — exactly one XML path per `Object_Kind` (`@kind`; `@type` is localized), no fallback chain:
- `Text_Content` — the visible static text: text object (kind 2, `Text/StyledText`), button (kind 10, `Button/Label/Text/StyledText`) and popover button (kind 14, `PopoverButton/Label/Text/StyledText`). FileMaker evaluates anchors typed into a label at runtime — merge fields (`<<Field>>`, unqualified always against the layout's TO, also inside a portal row), merge variables and layout calculations `<<ƒ:…>>` — but never a `{{Symbol}}`; the import resolves them accordingly (see `XMLLayoutReferences.Ref_Source`, `display_calculation` and `LayoutObjectSymbols.Is_Evaluated`). Catalogs imported before 1.33.0 have NULL here for buttons, and carry the popover-panel title formula instead
- `Label_Calculation_Text` — label formula of a button-bar segment (kind 10/14): FileMaker stores a segment label as a formula, even static text (`"Save"`). Label text and label formula exclude each other
- `Title_Calculation_Text` — title formula of a popover panel (kind 15, calc role `popover_title`) and of a tab panel (kind 12, `panel_title`). A popover segment of a button bar has an empty label — its visible label is the title of its panel
- Guard: P6 `v_check_layout_text_paths` (`text_path_mismatch` / `label_text_and_calc` / `title_path_mismatch`, all expected 0) compares the columns with the object's own raw XML

**Field entry (schema 1.31.0)** — only on field-bearing objects, NULL elsewhere:
- `Entry_Options_Raw` — raw `<Field><Options>` bitmask (kept because most bits are undecoded)
- `Entry_Browse` / `Entry_Find` — the entry rule per mode: `allow` | `select_only` | `view_only` | `by_calculation` (two bits per mode, identical in both SaXML profiles — see `xml-schema.md`)
- `Entry_Calculation_Text` — the formula of the `by_calculation` state, **one per object** (FileMaker offers a single formula for both modes). Written by SaXML 2.3.0.0 only: a FileMaker 22 export carries the same bits but no formula. Its calculation instance has the role `field_entry` — FileMaker files it under the same DDR key as the hide condition, so with two formulas only one of them carries chunks (the anchor is assigned by text comparison; the other instance exists without edges). Per-slot dependencies: `v_calculation_links`; since converter 2.30.0 the edges of the entry formula carry `Link_Subrole = 'field_entry'` (P4 retags the colliding DDR key `Hide` once the anchor is assigned, in `XMLCalcReferences`/`PluginFunctionUsages` and thus in every projected edge), so the raw `Hide` subrole only ever marks the hide condition — catalogs imported before 2.30.0 still carry `Hide` on both

**Polymorphic properties:** `Object_XML` — full object definition as a raw XML fragment, queryable via `xml_extract_text(Object_XML, '/xpath')[1]` (requires `LOAD webbed;`)

## PrivilegeSetRecordAccess (Custom Record Privileges)

When a privilege set uses **Custom Record Privileges**, the `<Records>` element only carries `Custom="True"` and `PrivilegeSetsCatalog.Records_*` no longer reflect the real access. The detail tree (`Records/Custom/ObjectList/Table`) is parsed into **PrivilegeSetRecordAccess** — one row per privilege set × table × operation:

- `PrivilegeSet_ID` / `PrivilegeSet_Name` / `PrivilegeSet_UUID` — owning privilege set
- `BaseTable_ID` / `BaseTable_Name` / `BaseTable_UUID` — target base table (NULL when `Table_Type='New'`)
- `Table_Type` — `existing` or `New` (the default rule for future, not-yet-existing tables)
- `Operation` — `View` | `Edit` | `Create` | `Delete`
- `Access_Mode` — `NoAccess` | `ReadOnly` | `ReadWrite` | `Calculation` | `Custom` | … (kept as VARCHAR, no enum, so unknown modes survive)
- `Calculation_Text` — plain-text formula (CDATA) when `Access_Mode='Calculation'`, normalized
- `DDR_Hash` — `Calculation/DDRREF/@hash`; JOIN-able with `DDR_Calculations.Calc_Hash`
- `Context_TO_Name` / `Context_TO_UUID` — evaluation context (the calc's table occurrence)
- `Fields_Access` — the table's `<Fields>@access` (one value per table; `Custom` opens a per-field detail tree → PrivilegeSetFieldAccess)
- `File_Name`

**Graph integration:** all references inside record-access calcs (via `DDR_Hash` → `DDR_Calculations`) are emitted into `XMLCalcReferences` with `Source_Type='PrivilegeSet'` and resolved to graph links (Link_Subrole = `<Operation>:<Table>` where applicable): **FieldRef** → `PrivilegeSet → Field (reads_field)`, **CustomFunctionRef** → `PrivilegeSet → CustomFunction (calls_customfunction)`, **PluginFunctionRef** → `PrivilegeSet → PluginFunction (calls_pluginfunction)` (via `PluginFunctionUsages`). **VariableReference** is handled separately — it has no generic XMLCalcReferences→link pass, so its read-usage is registered in `VariableUsages` (`Context_Type='record_access_calc'`) and becomes a `PrivilegeSet → Variable (reads_variable)` link. Together these close the where-used gap for any field/variable/CF/plugin referenced **only** by a Custom Record Privilege calc. Requires DDR-Info; without it the table is still populated (calc text comes from the CDATA subtree), but no graph links are created.

**Field level — `PrivilegeSetFieldAccess`:** when a table's `Fields_Access='Custom'`, the per-field detail tree (`…/Table/Fields/Field`) is parsed into one row per privilege set × table × field: `BaseTable_*`, `Field_ID`/`Field_Name`/`Field_UUID`, `Field_Type` (`existing`/`New`), `Access_Mode` (`NoAccess`/`ReadOnly`/`ReadWrite`), `File_Name`. Tables without custom field access produce no rows here.

**Other object classes — `PrivilegeSetObjectAccess`:** the same `Custom="True"` mechanism applies to Layouts, ValueLists and Scripts. Unified table with an `Object_Class` discriminator (`Layout`/`ValueList`/`Script`), one row per privilege set × object: `Object_ID`/`Object_Name`/`Object_UUID`, `Item_Type` (`existing`/`New`), `Access_Mode`, `Records_Access` (Layouts only), `Class_Allow_Create`, `File_Name`. Classes left in the simple attribute form (e.g. `<ValueLists Create="True" …>`) produce no rows.

Both feed the graph via **scoped restriction links** (`restricts_field` / `restricts_object`), but only for actual restrictions (`Access_Mode <> 'ReadWrite'`). **A restriction is *not* a usage** — these roles never make an object appear "used" in where-used or dead-code analysis. Folders/separators in the access tree are excluded. Link_Subrole carries the access mode.

## VariableUsages / VariablesCatalog

**VariableUsages** — every individual usage of a variable:
- `Variable_Name` — Full name including the prefix (`$sort`, `$$Module`)
- `Variable_Scope` — `global`, `local`, `superglobal`, `let_local`
- `Usage_Type` — `set` (assignment) or `read` (read access)
- `Context_Type` — `script_step`, `calculation`, `auto_enter_calc`, `custom_function`, `layout_object`, `record_access_calc` (variable read inside a Custom Record Privilege calc; Context_Name = `<PrivilegeSet> › <Operation>:<Table>`)
- `Context_UUID`, `Context_Name` — UUID and name of the context
- `Script_Name`, `Script_UUID`, `Step_Index` — Script context
- `Table_Name`, `Field_Name` — Field context
- `Source` — `set_variable_step`, `ddr_chunk`, `mbs_variable_call`, `merge_variable`, `regex_fallback`
- `File_Name` — FileMaker file

**VariablesCatalog** — aggregated overview per variable, one row per scope instance `(Variable_Name, Variable_Scope, Scope_Anchor)`; `local` and `let_local` rows additionally per `File_Name` (clone files share the script/context anchor):
- `Variable_Name`, `Variable_Scope`, `Scope_Anchor`, `Display_Name`, `Normalized_Name`
- `Set_Count`, `Read_Count`, `Script_Count`, `File_Count` — `File_Count` is 1 for `local`, `let_local` and `global` rows; only a `superglobal` row spans files (P6 check `v_check_variable_identity` flags a local row with `File_Count > 1`)
- `Files` (VARCHAR[]) — list of file names
- `File_Name` — file of the row (`superglobal`: the most frequent file)
- `Has_Spaces` — spaces in the name?
- `Source_Reliability` — `ddr`, `mbs`, `merge`, `regex`

**Data sources:** DDR_Calculations VariableReference chunks (primary), Set Variable steps, MBS superglobals (Variable.Set/Get), merge variables from layouts, LayoutObject formula hashes (Conditional Formatting, Hide, Tooltip, etc.), regex fallback for files without DDR, display-calculation recovery (`Source='display_calc_recovery'`, 2.20.0 — variables regex-matched from the recovered formula text of empty-ChunkList layout calculations).

**Prefix convention for Display_Name:** `$` → local, `$$` → global, `$$$` → superglobal (synthetic, MBS Plugin)

**ObjectCatalog integration:** Variables are registered with `Object_Type = 'Variable'`. UUID = `md5(Variable_Scope || '::' || Scope_Anchor || '::' || Variable_Name)` — the scope anchor is the script for local variables, the file for global variables, `__global` for superglobals. Local variables of clone files share the UUID (same script UUID): identity is `(Object_UUID, File_Name)`, and every variable edge points to the variable of its own file (superglobals excepted) — join `ObjectCatalog`/`VariablesCatalog` with the file, never on the UUID alone.

**ObjectLinks roles:** `sets_variable`, `reads_variable`, `displays_variable`

## DDR-Info support (optional)

Starting with FileMaker 21, the export option **"Include details for analysis tools"** adds detailed metadata.

**Check availability:**
```sql
SELECT Has_DDR_INFO, FileMaker_Version, Filename FROM XMLMetadata;
```

**DDR_ScriptSteps** and **DDR_Calculations** are always created, but only populated when `Has_DDR_INFO = 'True'`.

**Usage with conditional display:**
```sql
SELECT
    s.Script_Name,
    s.Step_Index,
    CASE WHEN (SELECT Has_DDR_INFO FROM XMLMetadata) = 'True'
         THEN ddr.Step_Text
         ELSE s.Step_Name END as Display_Text
FROM StepsForScripts s
LEFT JOIN DDR_ScriptSteps ddr ON s.DDR_UUID = ddr.Step_UUID;
```

### DDR_Hash for Calculated Fields & CustomFunctions

With FileMaker 21+ and DDR-Info enabled, **FieldsForTables** and **CustomFunctionsCatalog** carry a `DDR_Hash` column that joins to **DDR_Calculations** via `DDR_Hash = Calc_Hash`:

- `FieldsForTables.DDR_Hash` — hash for Calculated Fields (NULL for other field types)
- `CustomFunctionsCatalog.DDR_Hash` — copied from `CalcsForCustomFunctions.DDR_Hash`

```sql
-- Dependencies of a Calculated Field
SELECT f.Field_Name, f.Table_Name, COUNT(d.Chunk_Index) as Dependency_Count
FROM FieldsForTables f
JOIN DDR_Calculations d ON f.DDR_Hash = d.Calc_Hash
WHERE f.Field_Type = 'Calculated'
GROUP BY f.Field_Name, f.Table_Name;

-- Dependencies of a CustomFunction
SELECT cf.CF_Name, COUNT(d.Chunk_Index) as Chunk_Count
FROM CustomFunctionsCatalog cf
JOIN DDR_Calculations d ON cf.DDR_Hash = d.Calc_Hash
GROUP BY cf.CF_Name;
```

- PrivilegeSet → Field (reads_field) — field referenced by a Custom Record Privilege calc; Link_Subrole = `<Operation>:<Table>`
- PrivilegeSet → Variable (reads_variable) — variable read by a Custom Record Privilege calc; via `VariableUsages.Context_Type='record_access_calc'`. A *read*, not a restriction — counts for where-used/dead-code (unlike `restricts_*`)
- PrivilegeSet → CustomFunction (calls_customfunction) / PrivilegeSet → PluginFunction (calls_pluginfunction) — CF/plugin called by a Custom Record Privilege calc
- PrivilegeSet → Field (restricts_field) — field-level restriction; Link_Subrole = access mode. Scoped to restrictions only (`Access_Mode <> 'ReadWrite'`); **never counts as usage**
- PrivilegeSet → Layout/ValueList/Script (restricts_object) — object-level restriction; Link_Subrole = access mode. Scoped to restrictions only; folders/separators excluded
- PrivilegeSet → ExtendedPrivilege (grants_privilege) — which sets grant fmapp/fmxdbc/fmwebdirect etc. (access audit)
- Layout → Theme (uses_theme) — layouts carrying a `LayoutThemeReference` (theme cleanup: which themes are in use?)
- Layout → CustomMenuSet (uses_menuset) — layout-bound menu set (the built-in default id=0/"[File Default]" is normalized to NULL in P1 and produces no link)
- Script → CustomMenuSet (installs_menuset) — Install-Menu-Set steps (via `XMLStepReferences` Ref_Type='menuset')
- CustomMenuItem → CustomMenu (opens_menu) — submenu item (`isSubMenuItem="True"`) → the menu it opens (`CustomMenuReference/@id`, no UUID → P4 resolves via `(File_Name, Menu_ID)` against `CustomMenuCatalog`; menu IDs are file-local). A real usage, deliberately NOT `parent_menu` (the containment-style owner backlink): closes the where-used gap for menus that only serve as a submenu of another (those need not be menu-set members → `contains_menu` doesn't cover them) and makes the menu hierarchy navigable. Unresolvable target IDs (built-in menu / outside the corpus) reported by P6 `v_check_submenu_unresolved`
- LayoutPart → Layout (parent_layout, structural) — parts anchored to their layout; Link_Subrole = part type
- LayoutPart → Field (breaks_on_field) — sub-summary break field (`Part/Definition/FieldReference`); Link_Subrole = part type. Closes the where-used gap for fields used only as a sub-summary break
- Field → ValueList (uses_valuelist, Subrole `validation`) — field validation by value list (a VL used only for validation no longer appears unused)
- Field → Field (summarizes_field) — summary field → summarized field; Link_Subrole = operation (Total/Average/…)
- File → Layout (default_layout) — start layout from the file options
- File → Account (auto_login_account) — auto-login account from the file options (security-relevant; unresolved when the referenced account does not exist)
- Owner → Calculation (has_calculation, structural/containment) — every calculation instance hangs on its owner (Field/ScriptStep/LayoutObject/Layout/File/CustomFunction/CustomMenu[Item]/PrivilegeSet); Link_Subrole = `Calc_Role[:Calc_Index]`. **Never counts as usage** (variant A: the usage semantics stay on the owner-projected edges; Calculation → target is only the derived view `v_calculation_links`); being structural it also never enters LogicalLinks/ClusterEdges
- Layout/File → Field/CustomFunction/BuiltinFunction/PluginFunction (reads_field, calls_customfunction, calls_function, calls_pluginfunction) — layout-/file-level **script-trigger parameter** calcs (schema 1.22.0, harvested from `ScriptTriggers.Trigger_XML`); Link_Subrole = `ScriptTrigger_<id>`. Closes the where-used gap for objects referenced only in a layout-/file-trigger parameter
- Script/ScriptStep/Field/CustomFunction/LayoutObject/Layout/File/Calculation → BuiltinFunction (calls_function) — a built-in function call in a formula. **One node per function, language-independent** (schema 1.32.0): the import resolves the formula token against the standard reference, so `Length` and `Länge` are the same target, and the `Get(…)` pair plus its bare sub-parameter row collapse onto one node instead of producing two edges at two nodes. Consequence for counting: the edge count per function dropped with the normalization without a single call site being lost — it used to count the same call twice. Which reference function a node stands for is looked up in `BuiltinFunctionIdentity`, never derived from the name
- PluginFunction naming: qualified as `MBS:<Sub>::<Sub>` (e.g. `MBS:List.Sort::List.Sort`); PluginComponents aggregate as `MBS::<Component>` via `groups_into`. SubNames resolve in **two stages**: chunk-proximity pairing in P2 (`MBS_SubnameMap`) plus a plain-text recovery pass in P3.5 (FileMaker's DDR export drops the argument NoRef chunk when a comment sits next to the call or calls nest — the lexer recovers those from the calc CDATA). A `PluginFunctionUsages.Plugin_Function_Name` still reading bare `'MBS'` therefore means a **genuinely dynamic first argument** (`MBS($var; …)`) — such calls have no catalog object and stay unlinked by design. **Design functions are never PluginFunctions:** the SaXML export tags `WindowNames`, `DatabaseNames`, `LayoutIDs`, `ValueListItems`, … as `PluginFunctionRef` in the authoring client's language (`Fensternamen`); phase 1c re-types those chunks, so they register as `BuiltinFunction` — since schema 1.32.0 already **canonicalized at import time** (`Fensternamen` → node `WindowNames`), not canonicalized at query time — with `calls_function` edges. The chunk type also covers plug-ins without a namespace and unresolvable identifiers (deleted custom functions) — those stay PluginFunction

## Reference attachments (`ref` / `plugref`) — platform & OS tables

Not part of the solution catalog: two solution-independent reference DBs the
REST-API attaches read-only (`ref` = `reference/fm_spec.duckdb`, `plugref` =
`reference/plugin_spec.duckdb`; the fm-test direct path attaches them itself).
Full schema: fm-spec repo `db/schema.md` (fm_spec) and the schema page
`docs/fm-lab/schema/plugin-spec.md` (plugin_spec — bundled with every release,
provenance in its `reference_meta` table). The platform/OS layer in
brief:

- **`ref.step_compat`** — Claris runtime tri-state per step (NULL = Partial,
  see CLAUDE.md §7).
- **`ref.function_platform_affinity`** (≥ 1.12.0) — curated runtime affinity
  of functions (`go`/`dedicated` rows; affinity, never compatibility).
- **`ref.step_os_affinity` / `ref.function_os_affinity`** (≥ 1.13.0) — the
  curated OS sub-axis from the Claris help prose. **OS vocabulary strictly
  `macos|windows|linux|ios`** — `ios` is the operating system (hosts
  FileMaker Go AND Claris iOS SDK apps); runtime terms never appear in an OS
  column. Affinity classes: `exclusive` (only on the listed OS) /
  `unsupported` (source-true inverse — resolve against the host-OS set of the
  object's runtimes, never against all 4) / `variant` (runs everywhere,
  OS-dependent behavior; no findings consumption) / `os_probe`
  (functions only, `os IS NULL`: Get(SystemPlatform) & co — guard idiom,
  not a binding). Absence of a row = "Claris states nothing", never
  "runs everywhere".
- **`ref.runtime_os_matrix`** (≥ 1.13.0) — host matrix runtime × OS
  (`fm_env` = step_compat vocabulary + `odata` + `ios_sdk`); the ONLY
  sanctioned translator between the runtime and OS axes. `cloud` has no rows
  until its host OS is documented with a Claris source.
- **`plugref.plugin_function_platforms`** — verbatim vendor flags (MBS:
  binary per macos/windows/linux/server/ios_sdk axis).
- **`plugref.plugin_os_map`** (≥ 1.1.0) — curated fold of the vendor platform
  axes into the OS vocabulary (macos/windows/linux 1:1; `ios_sdk` → `ios`
  with qualifier `sdk-only`; `server` is a runtime statement — no OS row).
