# Skill: fm-generate-script

Generates FileMaker scripts as paste-ready `fmxmlsnippet` XML through a reference-driven pipeline: a canonical text draft, a deterministic lint, resolution of every object reference against your catalog (real IDs, not guesses), table-driven XML emission from the language reference, and a validation gate before delivery.

## What it does

Snippet XML is never hand-written from memory. The XML shape of every step comes from the [fm-spec](../Wiki/fm-spec.md) emission layer ([step_xml_map](../schema/fm-spec-tables/step_xml_map.md) and its option bindings), the IDs of every layout, field, script and value list come from your catalog, and the result passes a gate before it reaches you.

```
P0 CONTEXT   conventions + target objects, verified in the catalog
P1 DRAFT     the script in canonical text form, one step per line
P2–P6        fmgen.py run: normalize → lint → resolve → emit → gate
P7 DELIVER   snippet + resolution report + gate protocol + redelivery warning
```

A failure in lint, resolve or gate goes back to the draft with the findings; the pipeline never "continues with a warning" unless you decide so.

**Context first.** Naming language and function-name locale are taken from the code-generation registry or derived from the catalog (existing script names, comments) — never from the language of the conversation. Every object the script will touch is verified in the catalog before drafting; an ambiguous target file is asked for.

**The canonical text form** is the human-readable intermediate you can review: one step per line, step names in any of the eleven locales (canonicalised by lookup), parameters in one bracket group (`Set Variable [ $x ; Value: … ]`), fields as `TO::Field`, layouts as `"Name" (TO)`, scripts as `"Name"`, comments as `# text`, disabled steps with a `//` prefix. Calculations use canonical English function names. Objects that do not exist yet are declared as `{{NEW:Field:TO::Name}}` and surface in the report as *create before paste*; the same marker inside a calculation declares a custom function that is not in the catalog yet. List-carrying steps (sort orders, find requests, import field maps) repeat a group label per item.

**Resolution** replaces names with the real IDs of the target file and produces a machine-readable report: resolved references, objects to create first, assumptions. If the catalog holds no data for the target file, placeholders are used and the delivery says so explicitly.

**Target coverage.** FileMaker 22 and 26 write different clipboard forms for some steps (renamed elements in `Configure AI Account`, `Blanks last` in `Sort Records`, a calculated zoom in `Set Zoom Level`, the print and PDF steps). The reference carries both forms as *shape coverages*, and every run resolves against exactly one of them: the `FileMaker_Version` of the target file in the catalog decides (22.x → 22, 26.x → 26); `--coverage` is the only override and is named in the delivery. A target file the catalog does not know has no version — the pipeline stops and asks instead of guessing. The IR and the gate protocol record `coverage` and how it was chosen. An option that exists only in the FileMaker 26 form is refused for a 22 target with a lint hint; a set flag or mode that is worthless without its counterpart (the print-options flags of `Print PDF`, `From: Target` without a source in `Append PDF`/`Open PDF`, `Save to: Target` without a target in `Close PDF`) is a lint error too, because FileMaker would drop it silently on paste — the couplings are rows of [step_option_implications](../schema/fm-spec-tables/step_option_implications.md).

**Value forms.** A target slot accepts a field reference, a variable, or — in one documented case — only a variable, and writing the other form loses data without FileMaker saying a word. `Generate Response from Model` keeps its message history in a **variable**: the options dialog offers no field picker for that slot, and a field reference pasted into it arrives as a variable named after the field, with no diagnostic at all. A draft that writes one there is therefore refused at its own line, with the expected form spelled out; the reverse case (a variable in a slot that only takes a field) is reported the same way — as an error where the reference classifies that very option (`slot_kind` in [step_options](../schema/fm-spec-tables/step_options.md), since fm-spec 2.2.0), as a warning where the classification still comes from the step as a whole ([step_xml_map](../schema/fm-spec-tables/step_xml_map.md)). The same knowledge runs through every later phase: the resolver refuses the case without looking anything up, the emitter refuses a field reference rendered into a text slot, the gate checks the value form of every target slot in the finished XML, and the decompiler marks bare text in a target slot as lossy — so input that never passed the lint, hand-built or machine-generated, cannot slip through either.

**Transactions.** `Open Transaction` needs its `Commit Transaction` in the same script, a Commit needs a preceding Open, `Revert Transaction` is valid only between the two, transactions do not nest, and neither Commit nor Revert may sit inside an If block — every one of these pastes cleanly and then the **file refuses to save**. The lint stops such a draft at its own line; the rules are rows of [step_constraints](../schema/fm-spec-tables/step_constraints.md) (`requires_pair`, `requires_parent`, `save_invalid_nesting`, since fm-spec 2.2.0), not constants of the generator.

**Error codes.** A numeric literal a draft compares with `Get ( LastError )` is checked against the FileMaker error-code table of the reference ([error_codes](../schema/fm-spec-tables/error_codes.md), since fm-spec 2.8.0; ranges count — `5123` lies in `5000-5499`): a code the table does not list is a warning (the branch can never match a FileMaker error — a typo, a plug-in code or a custom code outside `5000-5499`), a code only the web publishing engine or a REST API returns is an informational finding. Neither stops the pipeline; on a reference without the table the check skips with a note.

**The gate** checks the emitted XML step by step and reports each check by name — including warnings you have to act on: enum values documented but not round-trip verified, custom functions called with the wrong number of arguments, variables used as a step target without a prior `Set Variable` (an opt-in house convention), steps with an entry in the registry of known FileMaker bugs ([step_constraints](../schema/fm-spec-tables/step_constraints.md) — the snippet is valid, FileMaker itself may lose or skew the marked data on copy or paste), boolean attributes outside their value domain (`True`/`False`, or the `Yes`/`No` the window-style attributes of `Go to Related Record` and `New Window` take — `xml_true`/`xml_false` in [step_options](../schema/fm-spec-tables/step_options.md); a localized build's own spelling is a warning), built-in functions the target FileMaker version does not have yet or no longer resolves (`origin_version`/`removed_in_version` in [functions](../schema/fm-spec-tables/functions.md) — `SetPersistentData` against a FileMaker 26 target), and options that were parsed but did not materialise in the emission. A skipped check is reported as skipped, never as passed.

## What you get

1. The snippet file path (and the XML inline when short).
2. The resolution report — resolved references with real IDs, new objects to create before pasting, assumptions.
3. The gate protocol summary — every failed, warned or skipped check by name.
4. The redelivery warning: pasting a snippet twice creates a second copy; snippet paste can only *add* scripts, not edit in place.
5. A verification recipe: paste, save, copy back to the clipboard and diff against the generated XML.

**Paste path.** FileMaker Pro → Scripts panel → paste. With the MBS Plugin installed, `MBS("Clipboard.SetMonitorEnabled"; 1)` converts XML on the clipboard into a FileMaker script object; without plug-ins, see the delivery notes in `references/paste-semantics.md`.

## Good to know

- **Editing existing scripts.** Before an existing artifact file is touched, a timestamped backup is written next to it. A re-pasted snippet is still a new copy of the script in FileMaker.
- **Exotic steps.** When the table-driven emitter cannot render an option, that step is authored against the reference's own example XML, spliced in, and the whole snippet runs through the gate again; the delivery says which step was hand-authored.
- **Session pin.** With `FMLAB_SOLUTION` set, the pipeline resolves against that solution's catalog (`--catalog-db solutions/<id>/db/fm_catalog.duckdb`).
- **fmIDE ActionScript** is an experimental second target (`fmgen.py actionscript`): the parsed steps are translated into fmIDE's action JSON with its own hard gate. Delivery requires a running fmIDE in the target file and is outside this skill's validation; the artifact comes with capability notes.
- **Reverse direction.** `fmgen.py decompile` turns a snippet back into the canonical text form and attaches notes to steps whose slots a clipboard round trip may already have lost. Editor chrome (`DisableStepCollapsed`, `Restore` on comments) and editor state are stripped and noted, never emitted. Under target 26 a FileMaker 26 snippet is read as is; under target 22 it is translated to the 22 form and every non-default 26 option is reported as *lossy*, because FileMaker 22 drops it on paste. When a snippet does not match the target shape, the other coverage is tried and the source is reported ("read as FM 26 shape"). A localized FileMaker build writes the window-style booleans of `Go to Related Record`, `New Window` and `Go to List of Records` in its own language (`Ja`/`Nein` in a German build): the decompiler reads them as the reference state and notes it — the defect is registered in [step_constraints](../schema/fm-spec-tables/step_constraints.md), the evidenced spellings live with the generator's read tolerance, an unknown spelling stays lossy. Import Records target fields are qualified with the step's table occurrence (`Coverage::ID`) so the text form resolves on the way back. Localized calculations come back in canonical EN — function names and the Get family as whole forms (`Hole ( Kontoname )` → `Get ( AccountName )`), never inside string literals or comments. The text form keeps every state FileMaker wrote: an enum whose display would be another option's value renders explicitly when that option is absent (`destination: LayoutNameByCalc`), a flag switched off against its default renders as `select_all: Off`, and the decompiler re-parses its own rendering — where the positional form would bind a value to the wrong option it falls back to the labeled form and notes it.
- **Mirrored values and dropped options.** `Save Records as PDF` stores its document title twice — as the `Title` option and as a bare calculation directly under the step — and FileMaker heals whichever half is missing on paste, the title winning over a divergent copy. The reference declares the copy ([step_mirror_elements](../schema/fm-spec-tables/step_mirror_elements.md), since fm-spec 2.6.0), so a draft writes `Title: "…"` once: the generator fills the mirror, the decompiler reads it as redundancy and notes a divergence, the gate flags an emission whose mirror is missing. The `appearance` attribute of the same step is discarded by FileMaker on paste whatever its value (`paste_dropped` in [step_options](../schema/fm-spec-tables/step_options.md)); a draft that sets it gets a warning and the emission leaves it out. A minimal `Save Records as PDF [ file:x.pdf ]` emits the zero-state PDF options FileMaker itself writes (all pages, printing and copying allowed).
- **Read residues** are documented, never silent: the FileMaker-generated default formula in `Save a Copy as XML`, the opaque `PlatformData` of `Print PDF`, a `<Text/>` marker next to a field target. Options the SaXML export never carries — registered in the reference as `saxml_omission` rows of [step_constraints](../schema/fm-spec-tables/step_constraints.md) (fm-spec 2.7.0): the zoom formula of `Set Zoom Level`, the `Option` flag of `Insert Embedding`, *automatically open* and *create e-mail* in `Export Records`, `Save Records as PDF` and `Close PDF`, the XSLT stylesheet of an XML export in a FileMaker 22 export — can only be read from a clipboard copy, never from the catalog; the decompiler notes the gap on such a step. The FileMaker 26 spellings the decompiler translates for a FileMaker 22 target come from [coverage_renames](../schema/fm-spec-tables/coverage_renames.md).
- The bundled references cover paste semantics and silent-failure catalog, MBS usage guidelines and a full worked example.
